# SPLBATCH 构造与注册优化方案

状态：P0/P1 已完成；P2 已按后续确认实现“内联轻量输入 + 直接支撑查找”，保留原预计算接口；P3/P4 尚未实施。见 [构造分项诊断结果](native_batch_construction_profile.md)、[P1 实现与验证](splbatch_p1_results.md) 和 [轻量 Bind 实现](splbatch_light_binding_results.md)。

## 目标与接口

用户继续逐条添加观测：

```cpp
channel.AddObservation(binding, observation);
```

SPLBATCH 负责识别共同支撑、创建或复用内部 batch、管理内部缓存。调用方不增加 span 分组、batch handle 管理或排序要求。轨迹提供观测依赖的参数，批处理库判断这些参数能否组成同一批，这是两个不同职责。

第一阶段保留 evaluator、SegmentBatchCostFunction 的数值计算和 A/D 的求解流程。观察频率仍是优化一步、更新状态与去畸变、associate。目标是减少重复元数据处理和分配，不改变观测集合、权重、先验或迭代次数。

原生适配阶段的历史 4 线程冻结窗口：D 构造 1.321 ms、求值 2.042 ms、矩阵装配 4.120 ms、析构 0.117 ms、核心总时间 8.539 ms；A 核心总时间 9.624 ms。该阶段完整回放中 D 构造为 1.876 ms。P0 已补充分项估计；P1 的收益使用重新交错运行的优化前后程序比较，不以这些历史计时直接作分母。

## P0：细分成本，保存当前基线

已完成：本次无探针构造均值 1.164 ms；诊断校准后的已归因开销中，Binding 构造约 37%、支撑识别约 25%、观测预计算约 4%、批次创建约 6%、原生 Jacobian 缓冲分配约 4%。校准分项合计仍比无探针总时间高约 0.10 ms，百分比是诊断分布估计，不是精确闭合的原生时间分解。优先验证 P1 和 P2 中低风险的 Binding 构造改进，P3 相应后移。

独立诊断构建记录以下项目，正式性能测试关闭诊断：

| 项目 | 需要记录的内容 |
| --- | --- |
| 输入 Binding 构造 | 时间、绑定数量、参数块数量 |
| 支撑识别 | key 构造/查找时间、连续命中、表命中、新支撑数量、碰撞比较次数 |
| 观测准备 | PrepareObservation 时间和调用次数 |
| 提交批次 | cost 创建、写入计划构造、参数注册的时间 |
| 原生缓冲 | 分配时间、分配次数、总容量、析构时间 |

每观测时钟读数会干扰毫秒级结果，因此诊断需报告计时开销；分配统计另跑，不用带探针结果作为正式速度。保留当前源代码及配套可执行文件、共享库与加载路径，确保 D 优化前后的对照不会意外加载同一个新库。

## P1：在 AddObservation 内自动识别并复用支撑

主要修改 `problem_batcher.hpp` 和 `batch_binding.hpp` 的查找辅助接口，保留公开的 AddObservation 和旧 Key 接口。

优化前每条观测都调用 `binding.Key()`，其中包含校验和动态数组复制。P1 已改成以下内部流程：

```text
检查 channel 状态和当次 loss scale
    ↓
直接比较输入支撑与 last_batch 的支撑
    ├─ 完整匹配：使用已有 batch 索引
    └─ 不匹配：对输入数组直接计算哈希
                  ↓
              内部支撑表查找
                  ├─ 完整匹配：使用已有索引
                  └─ 首次出现：完整校验，保存支撑描述并创建 batch
    ↓
使用本次输入 binding 执行 PrepareObservation
    ↓
追加 prepared observation 与本次 loss scale
```

实现要求：

- `last_batch` 保存索引，避免 pending_batches 扩容导致裸指针失效；只在成功追加后更新。
- 比较有序参数地址、参数尺寸和 support_signature。先检查数组长度，不能用截断比较判定相等。
- 哈希只用于定位候选项，碰撞后比较完整支撑。C++17 可使用 `hash -> 候选批次索引`，不用创建拥有动态数组的临时 BatchKey。
- 命中已经完整校验且保存为不可变数据的支撑时，不再重复做参数两两去重检查。未命中、非法尺寸或非法参数仍按原规则检查并报错。
- 保持首次出现的批次顺序和批内添加顺序；不遍历哈希表决定残差顺序，不要求调用方预先排序。
- 缓存限定在 channel 和当前建批周期内；不同 evaluator、参数布局不混用。
- 无论是否命中，仍用本次传入的 binding 准备观测。相同参数地址不意味着预处理上下文相同，不能把旧 context 自动套给新观测。
- 预处理或分配失败不能发布不完整 batch，也不能让观测与 loss scale 数组长度不一致。

这一步消除临时 key 的动态复制，并把完整校验和支撑保存限制到首次出现时。每条观测仍需要读取并比较少量参数信息，以及执行 PrepareObservation；不能承诺整个添加过程从 O(观测数) 降到 O(支撑数)。

这是推荐的第一项优化：调用方式不变，evaluator 和 batch 求值无需改动，有序和乱序输入都能使用。

实现采用 `unordered_multimap<size_t, size_t>` 保存哈希与候选批次索引，支撑描述由 `PendingBatch::binding` 拥有。首次支撑完整校验并成功追加后再发布；索引插入失败会撤回新批次。已有批次先准备观测，追加 loss scale 后若观测追加失败则回滚 scale，成功后才更新 `last_batch_`。缓存随当前 channel 的 Commit 清理。

增量兼容边界：新辅助函数仅供普通 `EvaluatorChannel` 使用。`BatchBinding::Key()`、`BatchKey`、`BatchKeyHash`、`ParameterBlockLayout` 的原有实现不变，`incremental_problem_batcher.hpp` 不修改，不在 Binding 内缓存 Key 或校验状态。增量路径的支撑迁移、partition/revision 判断、prepared slot 刷新和失效处理继续走原实现；P1 不自动加速增量路径。

## P2：降低进入 API 之前的 Binding 构造成本

后续已按用户确认实现轻量输入及直接数组查找，未单独实施下面原计划中的 reserve 步骤。C/D 使用新增 BindInput；旧 Bind 和 B 保留。原 PrepareObservation 接口不变，SLICT 在 dt 相同时允许复用已存 Binding，变化时用本次输入 materialize 后准备；该判断由库及适配管理。实现与测试见 [轻量 Bind 记录](splbatch_light_binding_results.md)。以下保留阶段设计依据。

P1 无法消除 `AddObservation(Bind(...), o)` 中已经执行的 Bind 分配。当前 SLICT Bind 每条观测向两个动态 vector 反复 push_back；重复支撑识别再快，也不能收回这部分时间。

按 P0 的占比决定是否开展此阶段：

1. 先利用已知参数块数预设容量，减少重复扩容。只在统一的 Binding 构造助手中处理，调用方不增加支撑缓存或区间判断。这会减少分配，不会彻底消除分配。
2. 若仍是主要成本，再引入常见小布局的内联存储或轻量绑定输入；超出内联容量继续支持通用布局。外部保持逐条 AddObservation，库在首次支撑出现时保存需要长期持有的数据。
3. 保留已有拥有存储的 Binding 输入路径。改变公开 vector 类型可能影响依赖具体容器类型的代码，因此轻量表示必须作为独立兼容性改造验证，不能声称只改容器就完全无影响。
4. 轻量视图只能在当前添加调用期间借用输入数组；内部批次必须拥有长期使用的描述。控制点数值仍通过原参数地址访问。
5. 不能为了复用完整 Binding 丢失本次 Context；如需要转换到 evaluator 要求的 Binding 类型，转换层必须保留本次预处理语义。

首轮不要求采用新的 Binding 表示，也不把它与 P1 混在一起计时。

## P3：减少原生注册缓冲的分配

修改 `native_batch.cpp` 的存储管理，不改变 SegmentBatchCostFunction 的输出接口：

- 注册时先记录 cost、参数指针、全局列和缓冲需求。
- 批次收集完成后计算各局部 Jacobian 块的偏移，分配一块统一 scratch 存储。
- 各 cost 仍接收原先布局的 `double** jacobians`；每个块保持行主序和原尺寸，指向 scratch 中互不重叠的区域。
- 所有尺寸确定后再发布指针，Evaluate 期间不扩容。固定控制点仍传空 Jacobian 指针。
- Entry 的参数指针、列索引等小数组按已知数量预分配。

这一步减少当前每个 batch、每个参数块各自分配的次数，同时保留全局 J 和原生求解过程。不能在报告中把它算作直接累加 H/g 的优化。

## P4：复用写入计划和跨轮工作区

后续根据 P0 和前三阶段实测排序，不预设这部分是主要收益来源。

写入计划可以参考现有 IncrementalEvaluatorChannel::WritePlan：按残差维度、参数尺寸及完整 Jacobian 结构缓存，使用 SegmentBatchCostFunction 已有的接收写入计划的构造接口。不能仅按 span 或 evaluator 类型判定所有布局相同；压缩 cost 等其他模板实例保留兼容路径。

跨轮先复用内存容量，不直接复用旧约束：

- 求解器持有工作区，每个建批周期重新添加当轮有效观测；未再次添加的旧观测不能留在目标函数中。
- 当前 Solve 会复制新的 State，因此每轮重新绑定参数地址。没有稳定参数存储和生命周期管理之前，不跨 Solve 保留旧参数指针。
- 只有在旧 cost 已释放、没有求值进行时才能回收或复用对应存储；Ceres 和原生 registry 分别遵守自己的所有权规则。
- 关联更新后的法向、平面偏移、权重及有效点集合必须刷新。预计算系数是否可复用，需要明确的时间与 Context 更新契约，首轮仍按观测重新准备。

已有增量模块要求应用提供兼容性判断和版本信息，不能直接把这些责任转交给用户来完成本方案。若后续采用它，应由库的绑定/更新层封装这些机制。

## 验证与性能判据

正确性检查覆盖：有序、乱序、交错支撑；相同时间但不同参数；相同指针但不同尺寸/签名；哈希碰撞；非法输入；临时 Binding 生命周期；context 改变但支撑不变；追加失败；固定参数；仅 IMU/仅 LiDAR；共享计划的所有权和布局。

原 A/B/C/D 因子、先验、求解和 Ceres 注册兼容性检查继续执行。P1 应保持首次出现与批内顺序；对冻结窗口检查 r/J、H/g、最终代价和 1/8 步状态。

性能按阶段分别测量：当前 D、仅 P1、P1+P2（若实施）、加入 P3。A 始终作为原生对照；修改公共 SPLBATCH 路径后也记录 C 的影响。

使用同一组 101 个 eee_03 冻结窗口，1/4/8/16 线程、每配置 5 轮、一次单步优化、独立进程轮换运行。记录 build/evaluate/assemble/destroy/total 的均值和 P95、峰值 RSS，以及诊断运行中的分配和命中计数。正式结果包含全部构造和清理成本，不把缓存创建偷偷移出计时。

跨轮缓存若实施，单独报告首次构造及稳态更新成本，按实际频率计算合计。冻结窗口通过后进行完整 eee_03 回放，检查相同扫描覆盖、每帧三次单步/去畸变/associate 和相同 GT 时间点的精度；约 1% 的整帧差异需重复回放确认。

先验目标是消除已确认的逐观测 key 分配和重复校验，并使总耗时下降；不预先承诺 build_ms 从 1.3 ms 降至某个具体数字。只有测量确认构造是主因后，才将 16 线程下 D 不慢于 A 作为后续验收目标。

P1 已单独实现并验证；本次继续完成 P2 的内联输入与直接支撑查找。相对重新测量的 P1，4 线程 D 构造从 0.888 ms 降到 0.736 ms（下降 17.2%），总耗时下降 2.9%；C 构造下降 33.9%。详见 [轻量 Binding 结果](splbatch_light_binding_results.md)。P3/P4 留待依据剩余成本决定，不混入本次改动。整个过程由 SPLBATCH 与后端内部管理支撑、batch 和缓存，保持用户正常逐条加观测的使用方式。
